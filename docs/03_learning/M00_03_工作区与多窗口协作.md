# 工作区为什么这样分层

本轮问题是长期迭代后难以区分“要执行什么、实际执行过什么、参考别人的什么”。因此用 scripts 保存操作入口、runs 保存单次执行证据、upstream 保存外部原始代码。算法开发将进入实际创建的 src，而不是修改上游或在 run 内复制项目。

另外三个入口分别负责不同问题：根 README 指路；overview 记录阶段事实；任务卡记录某个窗口做什么。不要在三处维护同一份状态，否则一个窗口完成后另两个入口仍会说未开始。

多个窗口共享磁盘，不共享对话记忆。接手人先读总览和卡片，核对负责人/范围；结束留下修改、证据、未确认项和下一步。人工认领有竞争条件，并非互斥锁；公共文件与设备冲突时协调顺序执行。

本轮没有搬动旧记录，只增加导航并保存编辑前快照。避免路径变化让模型生成器、来源哈希或历史复验入口失效。新增功能用任务卡→接口→最小实现→新 run→报告推进，不预建大量空模块。

实际改动、验证与边界见[整理报告](../02_milestones/M00_workspace_organization.md)，详细约定见[工作区手册](../01_project/WORKSPACE_GUIDE.md)。文档静态检查结果在报告链接中，不需要再运行机器人或训练来“验证文件夹”。

## 后续修订：小实验优先集中，复制能力需要验证

用户反馈仅有目录导航不足以约束新对话，且原先公共 src/scripts 的分层使小实验难以独立搬运。因此新增根目录[项目结构规范](../../项目结构规范.md)，作为可明确引用的结构契约，AGENTS 要求新窗口先读。

当前采用：新增简单实验默认集中在 experiments/<编号>_<用途>，README、代码、必要配置相邻，输出进入自身 outputs/<新ID>。既有站立控制不迁移。只有正式集成或确有共享需求才改公共模块，避免为了短程序搭框架。

复制独立性与“文件集中”仍有区别：父工程导入、硬编码路径、缺失网格或软链接都会令副本依赖原工程。规范要求用户提出导出时核对依赖，并从不同工作目录做最小验证；真实运行尚未做时准确标注。此次只检查规范与链接，没有假称现有站立代码已经可搬运，也没有启动仿真。
