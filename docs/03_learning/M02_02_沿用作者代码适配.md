# 沿用作者代码适配完整模型：读代码的顺序

本轮用户要求“原代码基本保留、少改参数、Python 放一个文件夹”。当前入口是 [E002](../../experiments/E002_original_controller/README.md)，不是把 E001 的代码重新换几个文件名。前版 E001 真实采用 37 维特权反馈，与原六状态/VMC不同；即使站立通过，也不满足这次保留原实现的要求。

先读最外层 controller.py：RobotSensor 取反馈，VMC 更新两腿几何，StateEstimator 更新六状态，LQRController 算左右控制，RobotController 按名字写六个电机。日志/验收放 simulation.py，不让它的世界坐标真值进入控制。其它 Python 均在 LQR_six 中。原 mymath.py 保持原样，Leg 只改包内 import；相对每个源文件的差异见 SOURCE_CHANGES.patch，不能把有实质变化的 vmc/get_state 写成“完全没改”。

## 名称、单位、方向放在哪里

get_sensor.py 的 IMU 名改为 base_ang_vel/base_lin_acc；前后驱动关节通过模型命名地址读取，不能把八个被动铰链误当电机。write_sensor.py 对应 act_lf0/act_lf20/act_lw、act_rf0/act_rf20/act_rw，并按 XML 限幅。这些 XML 用 motor，ctrl 是 N·m；旧的“设置轮速度/腿位置”辅助命名不适用。

当前左轮正转、右轮反转为同一前进方向。controller.py 的六行输出明确列符号：腿保留作者左负右正习惯，轮采用当前轴向。VMC 输出 J 的符号配合该写法，不能只在输出端试正负而不核对状态方向。

get_state.py 将轮半径改为 0.06 m，加上轮架转角、机身 pitch 与腿几何补偿。轮编码器测的是轮相对轮架角度；直接拿它乘半径，会把轮架随腿摆动当成地面滚动误差。第一次差分先设置初值，不能把 reset 跳变当速度。s 是里程计积分，日志另记其相对世界 X 的误差；侧倾后的里程计仍有误差，不能宣传无漂移定位。

## 最容易忽略的姿态坐标

本 XML 的 framequat/body 在静止时给出约 [0.5346,0.4151,-0.5900,0.4403]，等于模型机身的 body_iquat；与此同时机身 xquat=[1,0,0,0]。fullinertia 对角化后的惯性主轴与机身坐标不重合，不能把前者直接当机身 IMU 朝向。第一次照搬读取 orientation 的版本，在 t=0 就误判摔倒；原失败留在 E002 outputs。当前 get_sensor.py 显式返回机身 xquat，gyro/acc 仍按 IMU site 定义读取。没有改 XML 姿态、阈值或实际重力来掩盖它。

机身姿态由仿真提供，仍不等于已经有真机 IMU 滤波器。这个差异是传感器定义问题，不是 LQR 增益“大一点/小一点”能补偿的。

## 哪些地方不能只改名称和质量

原 vmc.py 的 get_phi/get_J 针对旧五杆，四个杆长不是当前完整后支路的等价描述。为了保留所有独立杆件与四处闭环，当前 vmc.py 只在几何层使用 equality Jacobian：

`J_passive * qdot_passive + J_active * qdot_active = 0`

由此消去被动速度，再把轮心相对髋轴的长度/角度 Jacobian 转成两主动电机坐标。虚功映射仍是作者熟悉的 `tau = J @ [F0, Tp]`。没有给被动轴添加 actuator，也没有把真实闭环换成串联机器人。这层读取仿真几何/速度，后续实机还需要由真实编码器解几何；当前没有宣称部署完成。

lqr_controller.py 继续显式写六状态 A/B/K、支撑 PID、roll/delta/yaw 和左右 control 函数。机身质量 16.877574 kg 与整机 21.054625 kg 要区分；0.06 m 轮径/真实质量、当前支撑点和拓扑变化意味着旧 K 也不能无条件照搬。新的 K 仍是六状态，而非把 37 维 K 包进原类名。离线矩阵生成与失败见 E002 REPORT，当前 lqr.py 保留旧推导参考并明确不参与实际控制。

左右腿同步和 yaw 方向也必须核对。早期原型未闭合这些修正，约 1 s 后支撑失效；之后恢复作者的双腿差动修正并更正 yaw 符号，才通过正式短测试。不能把早期失败动画或矩阵线性稳定当作非线性站立成功。

mympc.py 取自原 lqr+mpc 分支，仍是无约束预测求解后裁剪首步，并以 0.2 叠加 LQR。它与 E001 的全序列约束 MPC 含义不同，报告分别写明。新增求解异常抛错及计数，避免旧裸 except 静默输出零时被当成 MPC 成功。

## 复验与适用范围

从 E002 目录运行已有 mjlab 解释器：

```bash
PYTHONNOUSERSITE=1 /home/cofallen/miniconda3/envs/mjlab/bin/python -B controller.py
PYTHONNOUSERSITE=1 /home/cofallen/miniconda3/envs/mjlab/bin/python -B controller.py --case push --duration 30
PYTHONNOUSERSITE=1 /home/cofallen/miniconda3/envs/mjlab/bin/python -B controller.py --control lqr-mpc --case push
```

先后两个 +0.03 rad 冒烟（LQR/叠加 MPC）通过；随后八项固定参数评测通过，其中 LQR 的前倾/推力各 30 s；另有异地默认 10 s 通过。每次结果独立保存，不覆盖原失败。完整命令和指标在 [REPORT](../../experiments/E002_original_controller/REPORT.md)，不是沿用旧 18 个案例冒充本轮结果。

上述站立评测本身不依赖 GUI 或录像；其他机器/环境、键盘/VOFA、实物、GPU/Isaac 或硬实时仍未验收，不把六状态结构等同于可部署状态估计。下一步应逐项核对 IMU、主动编码器、被动坐标求解和采样时序，保持当前文件格式继续修改。

## 追加：怎样真正“看到腿站立”并能开动

用户最初的窗口里只有关节在小数点后变化，鼠标拖动也没有反应。这里有两个独立原因：一是当时只有站立控制，没有任何速度/转向目标，平衡控制器本来就会把机器人按在原地；二是主循环每一步都执行 `data.xfrc_applied[:]=0`，连 MuJoCo 窗口 Ctrl+拖动写入的扰动力也一起清掉了。现在只在无窗口运行和 `push` 案例里清外力，窗口里可以推动机器人；无窗口轨迹仍与加入功能前逐值一致。

**录像与物理分开。** `render_stand.py` 只读 `model/data`，按仿真时间栅格取帧，通过管道交给系统 ffmpeg；帧率与主循环步长无关，HUD 用 Pillow 画在画面底部。MuJoCo 的离屏后端要在 `import mujoco` 前选：本机有 DISPLAY 时 GLFW 约 15 ms/帧，纯 EGL 软件渲染约 342 ms/帧，所以 `--video` 默认优先 GLFW，无显示才用 EGL；用户可用 `MUJOCO_GL` 覆盖。第一次实现用“上一帧时间 + 1/fps”取帧，实际 30 fps 只录到 296 帧（9.87 s），改成固定时间栅格后是 301 帧；这类问题只看导出帧数就能发现。

**键盘驾驶不是直接加轮子力矩，而是改 `Leg.target`。** 速度：`target['dot_s']=v`，同时令 `target['s']=实测 s`，这样六状态 LQR 只做速度跟踪，不因为里程计积分产生位置误差。原地转向：把速度目标改成实测 `dot_s`，否则轮子侧滑造成的假速度会通过 6 状态反馈和转向力矩互相拉扯，转向会越转越歪。转向本身用作者已有的 yaw 通道：`target['yaw']=yaw+rate/kp`，代入 `dF=kp*(target-yaw)-gyro` 得到 `dF≈rate-gyro` 的速率环；不需要另写一套偏航控制器。

**为什么保留绝对航向会坏。** 试过“转到某个航向后把 `target['yaw']` 固定、再制动”，以及先斜坡转到位再停。两者都在转向结束后的制动段失稳；日志里先是 `theta` 速度变大，随后轮子力矩到 ±5 N·m 限幅，六状态速度估计出现几十 m/s 的假值。改成速率控制、松键只保留阻尼、制动从实测速度无跳变开始后，0.3 m/s 行驶、0.2 rad/s 原地转和两者同时进行都能稳定 10–12 s。原地 0.3 rad/s 以上仍会倒，已从命令范围里撤掉；这不是“调一调就更好”的结论，而是当前 6 状态 + P 型 yaw 通道的边界。

**按键语义。** MuJoCo 的 `launch_passive(key_callback=...)` 只把按下事件转给 Python（实测 W/A/S/D/空格各只收到一个整数），所以命令只能锁存：按 W 数次加速，X 停车，不是按住才走。窗口必须先获得焦点，左右上角的提示和左下角状态由 `viewer.set_texts` 显示；控制台也逐条打印。

**实测。** 两段 10 s 录像（iso 与 side）都是 960x540、301 帧，轨迹与加入功能前的 `145716` 逐值相同；桌面窗口实际打开并截到站立的机器人（`outputs/viewer_check_20261109_155757_090862/`）；12 s 键盘端到端用 XTest 向真实窗口发 W/W/W、X、A、X，最终 x=0.417 m、yaw=0.082 rad、max_tilt=6.7e-06。被动窗口的 GUI 渲染让仿真比实时慢约 2 倍（20 Hz 刷新，10 s 仿真约 20 s 墙钟），所以键盘驾驶看起来偏慢；需要精确时长/速度证据时仍用离屏录像或无窗口运行。没有做实机、长时间驾驶或其它机器验收。
